## 1. Противоречия и расхождения между документами

### 1.1 Порядок модификаторов и реальный пайплайн

- **Spec (FR-202)**: порядок явно указан как `sex_delta` (008), затем `age_delta` (010). В коде 008 **sex уже запечён в base_vector** при построении identity — отдельного «sex_delta» в `assemble_state` нет.
- **SDD** это корректно поясняет («params_base уже включает 008 sex shift»), но в **spec** формула вводит в заблуждение: там написано `params_base + ... + sex_delta + age_delta`, тогда как фактически в сборку передаётся только `age_delta_32`. Для читателя спеки неочевидно, что «sex_delta» — это историческое имя, а не ещё один аргумент.
- **Рекомендация**: В spec явно указать: «В текущей реализации 008 sex входит в base_vector при построении identity; в assemble_state добавляется только age_delta_32 (и при необходимости memory_delta).»

### 1.2 Strict mode vs «age_mode как off»

- **Spec (Edge Cases)**: «Missing birth_datetime_utc: age_mode MUST act as "off" **or error in strict mode**.»
- **Plan / SDD**: везде зафиксировано «нулевая дельта для совместимости»; про strict mode нигде нет: ни флага, ни контракта, ни в tasks.
- **Итог**: strict mode объявлен, но не спроектирован и не в задачах. Либо убрать из спеки, либо ввести `age_strict_mode: bool` и задачу на fail-fast при отсутствии birth_datetime_utc.

### 1.3 BehavioralCore и memory_delta

- **SDD (п. 6.4)**: признаётся, что сейчас `apply_transits` не принимает memory_delta, и предлагается вариант (A) — расширить сигнатуру. **Plan** и **tasks** предписывают добавить в `apply_transits(..., memory_delta=None, age_delta_32=None)`.
- **Риск**: В 006/текущем коде `run_step_v2` при наличии memory_delta собирает состояние **сам**, без вызова Agent.step(). Если мы добавим memory_delta в BehavioralCore, но не добавим его в Agent.step(), то при replay с memory через Agent возрастная дельта будет, а memory — нет (или наоборот), и порядок модификаторов/делегирование останутся половинчатыми.
- **Рекомендация**: Явно решить в спеке/плане: (1) Agent.step() получает опциональный `memory_delta` и передаёт его в apply_transits, и run_step_v2 везде делегирует в Agent.step(), **или** (2) 010 не трогает memory_delta и в apply_transits добавляется только age_delta_32; тогда при наличии memory_delta сборка по-прежнему делается в run_step_v2 с вызовом assemble_state(..., age_delta_32=...). Сейчас в документах смешаны оба варианта.

## 2. Неоднозначности и недоспецификация

### 2.1 «1 день» для Lipschitz

- Условие: `max_abs(age_delta_32(t+1d) - age_delta_32(t)) <= age_daily_lipschitz`.
- Не определено: что считается «1 день» — ровно 86400 секунд, календарный день UTC, или «следующий вызов step() с датой +1 день»? При шагах не по дням (например, раз в неделю) Lipschitz применяется к **разнице между текущим и предыдущим вызовом**, а не к календарным суткам. Тогда за неделю дельта может измениться на 7*L по компоненте, что формально не «day-to-day».
- **Рекомендация**: Зафиксировать: «Lipschitz ограничивает изменение **между двумя последовательными вызовами compute()**; константа L интерпретируется как максимальное изменение на один **календарный день**; при шаге Δt дней допустимое изменение по каждой компоненте — min(Δ_component, L * Δt_days)» — либо явно отказаться от масштабирования по Δt и писать «per-call cap L».

### 2.2 Преобразование date → injected_time_utc

- **Data-model**: «При передаче date реализация должна однозначно преобразовать в datetime (например, полночь UTC этого дня).»
- Не задано: какой именно момент дня (00:00:00 UTC или локальная полночь, сведённая к UTC). Для возраста при шаге по дням обычно достаточно 00:00 UTC; но если в системе есть timezone в birth_data, возможна путаница.
- **Рекомендация**: Явно указать в data-model: «injected_time_utc при аргументе type date = date в 00:00:00 UTC (datetime(date.year, date.month, date.day, 0, 0, 0, tzinfo=timezone.utc)).»

### 2.3 birth_datetime_utc при варианте B birth_data

- В 006 data-model вариант B — только positions (и опционально aspects), без datetime_utc. В 010 при варианте B birth_datetime_utc отсутствует.
- Не сказано: можно ли в варианте B добавить опциональное поле `datetime_utc` только для 010 (и не использовать его для ephemeris). Без этого при «positions-only» натале возраст всегда выключен.
- **Рекомендация**: В data-model 010 явно написать: «Вариант B: если передан только positions без datetime_utc, birth_datetime_utc для 010 отсутствует; при age_mode=on используется нулевая age_delta_32. Для расчёта возраста в варианте B допускается опциональное поле datetime_utc в birth_data (не влияет на построение натала).»

### 2.4 Порядок признаков в age_stage_features

- В spec порядок перечислен: maturity, saturn_event, jupiter_return, nodal_return, uranus_opposition. В data-model таблица с j=0..4 совпадает.
- W_age в спеке задаётся по именам признаков (maturity, saturn_event, ...); в коде нужен фиксированный порядок индексов j. Один раз перепутать j=2 и j=3 — и интерпретация сломается.
- **Рекомендация**: В data-model и в коде завести константу порядка (например, `AGE_STAGE_FEATURE_ORDER = ("maturity", "saturn_event", "jupiter_return", "nodal_return", "uranus_opposition")`) и в плане/контракте требовать единственный источник истины для индекса j.

## 3. Риски и граничные случаи

### 3.1 Детерминизм при stateful AgeEngine

- AgeEngine хранит `_last_age_delta_32`. Replay означает: одна и та же последовательность (birth_dt, config, dates[]) должна давать те же output hashes.
- Если пользователь создаёт Agent один раз и вызывает step(d1), step(d2), step(d3), то состояние Lipschitz однозначно. Но если replay воспроизводится как «создать Agent, для каждой даты вызвать step(date)», то порядок вызовов фиксирован и детерминизм есть.
- **Риск**: Если в будущем step() будут вызывать в другом порядке (например, параллельно по датам) или переиспользовать один Agent с «перемоткой» времени назад, состояние Lipschitz перестанет соответствовать спецификации. Спека не запрещает вызов step(d2) после step(d1) с d2 < d1.
- **Рекомендация**: В spec или data-model явно указать: «Порядок вызовов step(date) MUST быть монотонным по времени (или реализация MUST не хранить Lipschitz state между вызовами при не-монотонной последовательности).» Либо описать поведение при «шаге назад» (например, сброс _last_age_delta_32 при обнаружении отката времени).

### 3.2 Первый вызов compute() и Lipschitz

- SDD: «при первом вызове — сырая дельта без сглаживания или нули». Если использовать нули, то на первом шаге изменение может быть до age_max_param_delta (0.06), что много больше age_daily_lipschitz (0.001). Success criteria требуют smoothness только для «1-day time change», но не для «первого дня жизни».
- **Рекомендация**: Явно разрешить на первом вызове (prev is None) выдавать raw_delta_32 без Lipschitz, с пометкой в инвариантах: «Smoothness гарантируется для пары последовательных вызовов с разницей дат ≥ 1 день после первого вызова.»

### 3.3 Отрицательный возраст

- FR-010: clamp(..., 0, age_max_years). Если по ошибке injected_time_utc < birth_datetime_utc, возраст станет 0. Спека не требует fail-fast.
- **Рекомендация**: Либо оставить clamp(0) и кратко упомянуть в Edge Cases («injected_time_utc < birth_datetime_utc → age_years = 0»), либо ввести проверку и ошибку в strict mode.

### 3.4 Population guardrails (Success Criteria 5)

- «No axis mean shift > 0.05 solely due to age at any single age slice» и «Adjacent age slices (±1 year) have axis mean deltas < 0.02» — это проверки на популяции (N≥10k, ages 0–90).
- В tasks нет явной задачи на скрипт калибровки/guardrails для 010 (аналог 009 calibration). T020 помечен как optional и про пики saturn/uranus, а не про mean shift и adjacent slices.
- **Рекомендация**: Добавить в tasks фазу или задачу: «Скрипт/тест популяционных guardrails: N≥10k, ages 0–90, проверка axis mean shift и adjacent age slice deltas по Success Criteria 5», и в плане указать, где он живёт (например, scripts/010/calibration_guardrails.py).

## 4. Пробелы в спецификации

### 4.1 Валидация конфига

- Указаны только age_mode ∈ {off, on} и дефолты. Не заданы: допустимые диапазоны (age_strength > 0? age_max_param_delta в (0, 1]? age_daily_lipschitz >= 0? age_max_years > 0?). При некорректных значениях возможно деление на ноль (например, width в bump) или бессмысленные границы.
- **Рекомендация**: В data-model или spec добавить раздел «Validation»: минимальные/максимальные значения и поведение при нарушении (fail-fast или clamp).

### 4.2 Формат debug-вывода

- FR-011 и User Story 4 требуют age_years, age_stage_features, age_delta_32_stats при debug. Не определено: это поля в StepResult, отдельный dict, или часть существующего state_log. Для 008/009 в коде есть StepResult и debug_009.
- **Рекомендация**: Указать в data-model или spec: «При debug step() возвращает (или дополняет результат) полями age_years: float, age_stage_features: tuple[float, ...], age_delta_32_stats: dict» и ссылку на тип StepResult / структуру лога.

### 4.3 Константы периодов и воспроизводимость

- Константы зафиксированы (29.5, 11.86, 84, 18.6). Если в будущем они станут конфигурируемыми, configuration_hash должен их включать. Сейчас в data-model сказано «можно не включать; если станут конфигурируемыми — включить», но не сказано, что при смене констант без смены age_profile воспроизводимость replay ломается.
- **Рекомендация**: Явно: «Константы периодов входят в replay-relevant state при age_profile=v1; при изменении констант configuration_hash или отдельный age_constants_hash должны меняться.»

### 4.4 Отсутствие Clarifications

- В 006, 008, 009 в начале spec есть блок Clarifications (сессия, Q&A). В 010 его нет. Часть неоднозначностей выше могла бы быть снята там.
- **Рекомендация**: Добавить секцию Clarifications с ответами на: strict mode да/нет, определение «1 day» для Lipschitz, порядок при memory_delta и делегирование в Agent.

## 5. Математика и семантика

### 5.1 bump при width = 0

- Формула bump(age, center, width) = max(0, 1 - |age - center| / width). При width = 0 — деление на ноль. В спеке ширины заданы константами (1.5, 1, 0.75, 2.0), но контракт функции не запрещает width=0.
- **Рекомендация**: В spec или SDD указать: width MUST be > 0; при width <= 0 реализация MUST raise или считать bump = 0.

### 5.2 Sigmoid и численная стабильность

- sigmoid(x) = 1/(1+exp(-x)). При больших |x| возможны переполнение или потеря точности. Для maturity x = (age_years - 25)/7, age_years в [0, 120], так что x в примерно [-3.6, 13.6] — в целом нормально, но стабильная реализация (например, clamp x перед exp) не упомянута.
- **Рекомендация**: В плане или SDD упомянуть: «Использовать численно стабильный sigmoid (например, при x >= 0: 1/(1+exp(-x)); при x < 0: exp(x)/(1+exp(x))).»

### 5.3 Дублирование весов в W_age

- В spec у разных признаков затронуты одни и те же параметры (например, big_picture_focus у maturity, jupiter_return, nodal_return; rule_adherence у maturity и saturn_event с плюсом, у uranus_opposition с минусом). Формула — линейная сумма по j, затем clamp. Семантика понятна, но калибровка «на глаз» может дать слишком сильный эффект по отдельным параметрам при одновременном пике нескольких признаков.
- Замечание не как ошибка, а как риск при калибровке: в Success Criteria 5 есть guardrails по axis mean, но не по per-parameter max contribution. При желании можно добавить в калибровку проверку по параметрам.

## 6. Задачи и план

### 6.1 Нумерация и зависимости

- T009 встречается дважды: в Phase 4 (AgeEngine) и в Phase 5 (T014 — «In Agent»). В Phase 5 T014 — это интеграция в Agent, а T009 — реализация AgeEngine; номера не дублируются, но стоит убедиться, что в Phase 5 нет опечатки (T014 vs T009).
- Зависимость T012–T016 от T009: пока нет AgeEngine, интеграционные тесты будут мокать вывод. Приемлемо, но в tasks можно явно написать «T015, T016 зависят от T014».

### 6.2 run_step_v2 и Agent.step

- В tasks не сказано, нужно ли менять run_step_v2: передавать ли в Agent.step memory_delta и вызывать ли assemble_state через Agent при наличии age_config. Если 010 не трогает run_step_v2, то при использовании replay с memory_delta и age_mode=on вызывающая сторона должна сама получать age_delta_32 (как?) и передавать в assemble_state — откуда брать age_delta_32 без вызова AgeEngine, не определено.
- **Рекомендация**: Либо задача «При наличии age_config в Agent и вызове run_step_v2 с memory_delta: run_step_v2 передаёт memory_delta в Agent.step() и использует единую сборку через apply_transits», либо явно ограничить scope 010: «Replay с memory_delta и age вместе поддерживается только при вызове Agent.step(date, memory_delta=...) в будущем; текущий run_step_v2 при memory_delta собирает состояние сам и для 010 не получает age_delta_32 (age тогда не применяется в этом пути).»
